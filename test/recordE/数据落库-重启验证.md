# 数据落库证明：进程重启后数据仍在（#19「操作后数据落库」）

- 被测版本：`main` @ `a7d70ff`
- 时间：2026-11-23 19:44
- 后端：`java -jar min-roamer-api-0.1.0-SNAPSHOT.jar --server.port=18087`
- 数据库：**H2 文件库** `jdbc:h2:file:<.tools/h2persist3>/roammin;WRITE_DELAY=0`
  （`WRITE_DELAY=0` 让每次提交同步落盘，避免强杀进程时丢失未刷写的数据）
- 脚本：`.tools/verify-persistence3.mjs`

## 做法

1. 启动后端（文件库），注册账号，`POST /api/v1/buddy` 发布一条搭子帖 → `id=1`
2. 等 1.5 s（同步刷盘），记录数据库文件大小
3. **强杀 JVM**（`SIGKILL`），确认端口不再响应
4. 用同一个数据库文件**重启一个新 JVM**，重新登录，`GET /api/v1/buddy/mine`

## 实际输出

```
--- boot 1 ---
[boot1] up pid=3120
register=201 create=200 postId=1
db file: roammin.mv.db(114688B)
--- force-kill boot1, start a fresh JVM on the same DB file ---
[boot2] up pid=3284
after restart: login=200 mine=200 posts=1 survived=true title=重启后应仍在的搭子帖
RESULT: PASS - 数据落库，进程重启后仍在
```

## 结论

- 搭子帖写入的是 `buddy_posts` 表（`BuddyPost` 实体），重启后 `GET /buddy/mine` 仍返回该帖，**证明数据真正落库**，不只是前端/内存状态。
- 登录在重启后仍成功（`login=200`），说明 `users` 表同样持久化。
- 本机踩坑记录（供其他人复现时避坑）：
  - 默认 `./data/minroamer` 或**继承只读属性的旧 `.mv.db`** 会报 `SQL Error 90097 database is read only`，`insert into users ...` 直接失败；
  - 换一个**全新目录**建文件库即可写入；
  - 不加 `WRITE_DELAY=0` 时，强杀 JVM 会丢掉尚未刷写的数据（此时「重启后仍在」验证会失败，属进程被杀而非业务缺陷）。
- UI 侧的「刷新后仍在」仍用 H2 内存库跑（见 `README.md`），避免测试数据越积越多。
